# Own watcher lifetime at public write seams

A live watcher is exclusive across both its application root and resolved SQLite database, so every public writer must enforce the same App Data Lifetime Lease rather than relying on a particular CLI, tray, or Web UI caller. `watch_vrc_logs()` therefore acquires the OS-backed app/database lease itself, while `LiveAppSessionRuntime` may acquire it synchronously for immediate conflict feedback and hand that verified lease into the watcher Module. The shared Data Operation runner acquires the same lease before dispatching every bulk workflow, so Web, CLI, threads, and processes cannot overlap a Data Operation with another Data Operation or a watcher; Web conflicts return HTTP 409. Ownership begins before startup maintenance or capture creation and ends only after settlement, database commits, artifact cleanup, and finalization; the persistent lock files are locators, not runtime state. Web UI startup maintenance uses the same lease: active ownership is an expected skip, while configuration, SQLite, schema, repair, and commit failures remain visible as startup warnings. The unsafe `rebuild-data` workflow remains available only through the explicit CLI path until it can preserve all durable evidence and user decisions; it is absent from the Web catalog and rejected by the Web operation endpoint.
